## 4. Critical issue found & fixed (this session)

**Finding (from code review):** leading-zero CEP/zip codes were being **silently stripped to integers**. Confirmed real:
- Raw: **245,733** geolocation + **23,995** customer zips begin with `0` (e.g. CEP `04106`).
- Cleaned (before fix): **0** leading-zero zips remain (`04106` → `4106`).
- Affected: `olist_master.customer_zip_code_prefix`, `geolocation_clean.geolocation_zip_code_prefix`, `Dim_Geography.zip_code_prefix`.

**Root cause:** `data_preparation.load()` read with `dtype={"zip_code_prefix": str}` but the geolocation column is named `geolocation_zip_code_prefix` (key mismatch → coerced to int64); `build_master()` read customers with default numeric dtype. So `zip` was corrupted on read, not on purpose (validation then could not even see the loss without a fixture).

**Fix applied:** `data_preparation.py` (a) `load()` now reads the header and sets `str` dtype on every `*_zip_code_prefix` column (+bare `zip_code_prefix`); (b) `build_master()` reads customers with `dtype={"customer_zip_code_prefix": str}`. Full regeneration of `02_Cleaned_data/` + star schema re-run.

**Post-fix:** all 7 zip tables preserve leading zeros (e.g. `olist_master` raw 23,995 → clean 23,255; `Dim_Geography` raw 245,733 → clean 4,354 after dedup). ✅ **Zip col must be `VARCHAR`/`TEXT` in PostgreSQL, never `integer`.**
